What changes

Native variable events capture individual credits and debits, including fast-track transactions whose net balance change is zero. Existing purchase and bonus actions supply reason labels. Native group events retain additions, removals and group resets. A two-minute scan keeps current balances and giveaway buckets in sync.

The import updates 17 existing actions from your supplied export. It adds audit calls and replaces the Points Ledger code. It contains no commands, queues or timers, and no auto-run action. Your existing config.js stays in place. No chat messages or giveaways are triggered by installing the tracking code.

4. Add the native balance listener

  1. Create one action named Voyager - Points Capture. Enable it, set its queue to Voyager Points, and leave Concurrent off.
  2. Add trigger Core → Global Variables → User Global Variable Updated.
  3. Set Persisted = Yes, leave Variable Name and User Login blank, and choose Platform = Any. The code filters to the configured points field on Twitch, YouTube and Kick.
  4. Add one sub-action Core → C# → Execute C# Method. Select code Voyager Points Ledger and method RecordMovement. Leave Run on UI Thread off.

Do not paste another copy of the ledger code into this action. All listeners must call the same named code instance so file writes are serialized. Keep only one balance listener. The existing ledger action retains its timer trigger.

7. Check one movement before relying on the totals

  1. Keep the listeners enabled. Use your own test account and note its balance. Through your existing administrator point action, add a small known amount, then remove that same amount.
  2. Refresh the Points page. Native events received should appear. History should contain two movements with the right before/after balances even though the account ended where it started. Credits and debits should each increase by the test amount.
  3. Use your normal next successful !upgrade to verify the purchase label and bucket contribution. They should have the same Ref when matched. A denied purchase should add no debit.
  4. Check the next fast-track purchase: its credit and purchase should appear separately from !upgrade spending.
  5. Check the next real tier change and the next update on each connected platform. If labels are awaiting events or the capture error text appears, check the listener, named code and Action History before trusting totals.

How to read the dashboard

MeasureMeaning
Current pointsLatest saved balance, including negative values if your existing actions produce them.
Captured credits / debitsIndividual numeric changes delivered by the native variable listener. Member totals exclude bucket accounts. Snapshot deltas are never added again.
Earned rewardsIncoming changes matched to a reward/bonus hook. A subset of credits, not a lifetime total.
!upgrade spendingMatched deductions from your command upgrade path. Other membership purchases and promotional fast-track purchases are separate.
UnclassifiedThe amount is captured, but its reason could not be matched. This includes manual edits, some bulk/StreamUP DLL writes, failed hooks or concurrent changes. No reason is guessed from an amount alone.
Reconciliation differenceCurrent balance minus capture opening balance plus debits minus credits. A difference can indicate queued events, a gap, a reset or an unobserved change. Missing values stay unknown.
Snapshot / reconciliationA periodic balance or membership reading. Useful for finding gaps; not a transaction and not included in movement totals.
Variable created / removedIf an old or new value is unknown, the record is retained without pretending the missing value was zero. Bulk deletion can also be noticed by the scan.
Legacy totalsYour v2 snapshots, observed increases and upgrade audits stay in member history. They are separate from the new capture counters.

Reason hooks match user ID, field, expected before/after change and the variable's LastWrite timestamp. A mismatched or conflicting label stays unclassified. A shared Ref links a matched purchase debit with its bucket credit; bucket credits are not counted again as member earnings.

The History search covers the saved journal, with platform, date, movement, tier and bucket filters. Export full history CSV exports all history regardless of these filters. Member CSV follows the member filters. Dates on screen use the browser's local timezone; CSV timestamps use UTC.

Coverage and history

Keep Streamer.bot running with the listeners enabled. The page may be closed. Refresh is every two minutes; event capture occurs when the native events run. No listener can recover transactions from before installation or during downtime. A missed-event interval can contain offsetting changes that a later balance scan cannot detect.

Journal entries are appended before checkpoint updates. Checkpoints are saved at most every five seconds during event traffic and on scans; journal replay restores committed records after restart. Duplicate movement deliveries are identified by user, field, write time and values. Deliveries over 48 hours late are ignored rather than guessed. Keep system time correct.

History is retained in daily ledger-YYYY-MM-DD.jsonl files alongside checkpoint.json. Back up the entire folder while Streamer.bot is closed. CSV is a report, not a complete operational backup. Do not delete individual journals or restore a checkpoint without its matching archive. For exports over 100,000 records, use the journal archive.

Updated actions and rollback

The import retains the existing action IDs, membership actions, animation steps and non-watchtime reward rules. Audit calls surround their writes. Watchtime is the deliberate exception: both the older and newer Present Viewers paths now share a fixed +1 per viewer every 10 minutes while live. StreamUP Present Viewers amounts and boosts do not multiply that award. See WATCHTIME_SETUP.html for eligibility and installation. Restoring the original rollback import also restores the old watchtime rate.
